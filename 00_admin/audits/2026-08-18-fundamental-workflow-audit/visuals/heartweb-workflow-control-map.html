Für den Call

90-Sekunden-Erklärung

  1. Wir haben zuerst einen kundenneutralen lokalen Core gebaut, damit keine Notion-Automation fachliche Regeln umgehen kann.
  2. Jede fachliche Änderung erzeugt einen typisierten Command, wird im Core validiert und als Event protokolliert.
  3. Notion zeigt akzeptierte Events als Projekte, Tasks, Gates, Reviews, Blocker und Performance-Daten.
  4. Ein menschlicher Edit in Notion wird als Vorschlag zurück an den Core geschickt. Erst die akzeptierte Antwort wird wieder projiziert.
  5. Heute müssen wir Notion-Struktur, Personenmapping, Feldverantwortung und Live-Transport festlegen.
Nicht verhandelbare Leitplanken

Damit die Integration sicher bleibt

Notion darf Status, Freigabe, Artefakthash oder Revision nicht direkt verbindlich ändern.
n8n darf keinen Gate-Entscheid erfinden und keinen Run selbst abschließen.
Doppelte und verspätete Events müssen idempotent und revisionsbewusst verarbeitet werden.
Operatoren arbeiten trotzdem primär in Notion. Technische Details bleiben hinter Links oder Spezialansichten.

Empfohlener Pilot

Erster Notion-Vertical-Slice

Nicht sofort alles anbinden. Zuerst einen vollständigen, sichtbaren Kontrollkreis:

Project -> Run -> Step -> Task -> GATE-1 Review -> Revision Request -> Core Validation -> Event -> aktualisierte Notion-Projektion

Damit testen wir Identität, Relationen, Human Review, Konflikte, Reprojection und Operatorverständlichkeit in einem einzigen Flow.
